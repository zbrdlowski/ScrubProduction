Create helper functions includes/permissions.php
<?php

$ACL = require __DIR__ . '/access_control.php';

function canAccessPage(string $page): bool
{
    global $ACL;

    if (!isset($ACL['pages'][$page])) {
        return false; // unknown page = blocked
    }

    $rule = $ACL['pages'][$page];

    if ($_SESSION['permission'] < ($rule['min_permission'] ?? 0)) {
        return false;
    }

    if (!empty($rule['departments']) && !in_array($_SESSION['dpt'], $rule['departments'])) {
        return false;
    }

    return true;
}

function canShowMenu(string $menuKey): bool
{
    global $ACL;

    if (!isset($ACL['menus'][$menuKey])) return false;

    return $_SESSION['permission'] >= $ACL['menus'][$menuKey]['min_permission'];
}

Enforce Security in index.php (IMPORTANT)

At the top of index.php:

require 'includes/permissions.php';

$page = $_GET['page'] ?? 'profile';

if (!canAccessPage($page)) {
    $_SESSION['error'] = 'Access denied';
    $page = 'profile';
}

include "includes/$page.php";


✅ This prevents URL-hacking
✅ Menu hiding alone is NOT security

prístup k ovládacím prvkom a editácii:

in some cases script needs to be accessible to let's say Basic operator, but columns or buttons must be disabled. or not displayed for them. (controlls like: Add, Edit, Delete...) only senior Operator or above can access it. How to ?

Excellent question — this is exactly where many systems go wrong, so doing it now is smart 👍
What you need is two-layer authorization:

✅ THE CORRECT MODEL (Industry-grade)
Page access → Can the user open the screen at all?
Action access → What can the user do on that screen?

You already solved #1.
Now we add #2.

🧱 CORE CONCEPT

Instead of just:
canAccessPage('items')


You introduce:

canPerform('items.add')
canPerform('items.edit')
canPerform('items.delete')


✔ Page loads for Basic operator
✔ Buttons/columns hidden or disabled
✔ Backend still protected

STEP 1: DEFINE ACTION PERMISSIONS
includes/action_permissions.php
<?php

$ACTION_PERMISSIONS = [

    // ITEMS
    'items.view'   => 100,
    'items.add'    => 200,
    'items.edit'   => 300,
    'items.delete' => 400,

    // ORDERS
    'orders.view'   => 100,
    'orders.create'=> 200,
    'orders.send'  => 300,
    'orders.delete'=> 400,

    // EMPLOYEES
    'employee.view'   => 300,
    'employee.add'    => 400,
    'employee.edit'   => 400,
    'employee.delete' => 500,
];


This stays stable for years

🧠 STEP 2: HELPER FUNCTION
includes/permissions.php
require_once 'action_permissions.php';

function canPerform(string $action): bool
{
    global $ACTION_PERMISSIONS;

    if (!isset($ACTION_PERMISSIONS[$action])) {
        return false;
    }

    return ($_SESSION['permission'] ?? 0) >= $ACTION_PERMISSIONS[$action];
}

STEP 3: FRONTEND CONTROL (Buttons / Columns)
✅ Hide buttons completely
<?php if (canPerform('items.add')): ?>
<button class="btn btn-success">Add Item</button>
<?php endif; ?>

✅ Disable button (visible but blocked)
<button class="btn btn-danger"
    <?= canPerform('items.delete') ? '' : 'disabled title="Insufficient permission"' ?>>
    Delete
</button>

✅ Table column visibility
<?php if (canPerform('items.edit')): ?>
<th>Edit</th>
<?php endif; ?>

<?php if (canPerform('items.edit')): ?>
<td>
  <a href="edit.php?id=<?= $row['id'] ?>" class="btn btn-sm btn-warning">Edit</a>
</td>
<?php endif; ?>

🔐 STEP 4: BACKEND ENFORCEMENT (CRITICAL)

Never rely on UI only

Example: save_item.php
require_once 'includes/permissions.php';

if (!canPerform('items.edit')) {
    http_response_code(403);
    exit('Forbidden');
}


✔ Even if someone crafts a POST request → blocked
✔ Protects API, AJAX, CSV uploads, etc.

🧩 STEP 5: PAGE LOAD WITH LIMITED MODE

Sometimes you want logic like:

Same page, different behavior

Example:
$isReadOnly = !canPerform('items.edit');


Then:

<input type="text" <?= $isReadOnly ? 'readonly' : '' ?>>
